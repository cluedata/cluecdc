# v0.3.2 destination implementation status

The v0.3.2 plan contains four warehouse destinations:

1. Google BigQuery
2. Amazon Redshift
3. ClickHouse
4. Azure Synapse Analytics

The implementation preserves the earlier Azure control-plane work and extends
the existing pipeline/delivery lifecycle. It does not introduce Airbyte, a
second pipeline model, or a mandatory commercial connector. No release tag,
publication, push, or main-branch merge is performed by this work.

## Verification evidence and remaining sequence

- Backend regression suite, frontend tests, type checking, lint/format, image
  build, plugin discovery, production web build, strict docs build, Compose
  rendering, and Kubernetes rendering are recorded in the final implementation
  report rather than inferred here.
- Connector archives are checksum-pinned in the Connect image. The Java history
  transform is compiled and executed as part of that image build.
- The shared staged-runtime tests cover a failed upload with no checkpoint and a
  crash between destination apply and Kafka checkpoint.
- ClickHouse 26.8.20.9 accepted real target rows for synthetic Debezium create,
  update, and delete envelopes; composite-key JSON, Connect restart, and a
  temporary ClickHouse outage recovered successfully. The first run also proved
  that `exactlyOnce=true` incorrectly requires KeeperMap, so the default was
  corrected to documented at-least-once delivery.

Remaining work is external verification: run PostgreSQL and MySQL snapshot/CDC,
restart, replay, schema, key, and destination-outage matrices against each real
service. Only after those results are PASS should production readiness or a
current-state mode be advertised. ClickHouse current-state requires a proven
ReplacingMergeTree version/delete/query design; BigQuery, Redshift, and Synapse
require separately proven batch apply/MERGE semantics.

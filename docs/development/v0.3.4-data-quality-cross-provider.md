# PostgreSQL → MySQL Data Quality verification

The operator authorized adding and verifying PostgreSQL → MySQL support before
creating checks for the existing `PG 1` / `MySQL 1` Connections. The pair registry
now explicitly permits PostgreSQL/PostgreSQL, MySQL/MySQL and PostgreSQL/MySQL.
MySQL/PostgreSQL, other providers and non-current-state datasets remain blocked.

All six rule types can execute in the verified direction. COUNT rules compare
actual integers, not converted records. MAX timestamp rules retain common declared
semantics, explicit naive timezones, UTC MySQL TIMESTAMP sessions, activity/null/
future/skew diagnostics and BEST_EFFORT observations. Filter/window SQL remains
allowlisted, quoted, parameterized and read-only on each independent provider.

Schema Match does not infer lossless conversions from adapter availability.
Integer range/sign compatibility is certified. Known numeric narrowing and
timezone-contract changes fail; other unverified domains (text charset/collation,
numeric special values, date ranges, JSON and similar mappings) are inconclusive.
Matching observed timestamps does not make the full timestamp schema equivalent.

## Current dataset plan

Existing pipeline `Commerce pipeline` uses PostgreSQL
`cluecdc_source.public.customers` → MySQL
`cluecdc_destination.customers`, with an upsert delivery. Independent read-only
observations found two rows on each side and equal latest `updated_at` instants
(`2026-10-22T03:55:28.709860Z`). This attests the selected business timestamp from
the existing pipeline mapping; no continuous Source activity is assumed.

Prepared checks:

- `Customers - Count and last update`: row_count (Full Table, exact equality)
  and last_updated (UTC, business-update semantics, tolerance zero).
- `Customers - Schema compatibility`: compatible schema comparison including PK.
  It deliberately reports unverified text mappings and the PostgreSQL timezone
  contract versus MySQL TIMESTAMP; thresholds/types are not weakened to force PASS.

Both use manual execution, BEST_EFFORT and disabled notifications. The reviewable
payloads are `artifacts/data-quality/cross-provider/customers-checks.json`.
The operator explicitly approved applying the tested image to API and worker.
Those two services were updated and became healthy; Kafka, Connect, both database
containers, metadata and the web container retained their identities. No schema
migration or Source/Destination write was performed.

Both checks were saved through authenticated APIs and completed through the
durable worker. Count/last-update quality is PASS (2 rows each, zero timestamp
difference). Strict Schema Match is FAIL for the timestamp contract difference;
text/longtext mappings are explicitly unverified. These are quality findings,
not execution errors. The checks remain manual with notifications disabled.
Exact IDs, links, measurements, ownership/rollback plan and execution logs are in
`artifacts/data-quality/cross-provider/created-checks.json`, `runtime-plan.json`,
`customers-preview.json` and `runtime-apply.log`.

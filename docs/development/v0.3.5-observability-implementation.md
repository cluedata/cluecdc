## Architecture and compatibility

The independent collector runs alongside the existing job worker. PostgreSQL
`SKIP LOCKED` claims, 35-second leases, owner/expiry fencing and a unique
pipeline/sample bucket protect persistence. A short advisory transaction lock and
database time enforce the concurrency ceiling across worker processes. Scheduling,
claims and lease completion use the same database clock, including workers with
a simulated one-hour clock skew. Remote I/O
runs outside metadata transactions. Duplicate buckets do not evaluate alerts again;
missed intervals do not create catch-up jobs. No recurring generic Job or audit
record is created for each observation.

Defaults: 60-second collection (allowed 30–300), 180-second freshness, 10-second
provider timeout, 25-second collection budget, four concurrent collections and
seven-day raw history. Exporter, Connect and Kafka failures use bounded backoff.
Independent provider success survives other failures and collection cancellation.
Native Kafka work has its own deadline and a detached delivery copy, preventing late
threads from mutating published results. Cleanup removes at most 1,000 observability
rows per iteration and preserves legacy rows.

Four additive, authenticated `pipelines.read` GET endpoints read persisted state:

- `/api/v1/observability/summary`: bounded pagination, source/status filters.
- `/api/v1/pipelines/{id}/observability`: typed latest evidence and diagnostics.
- `/api/v1/pipelines/{id}/observability/history`: UTC range, seven days/500 points maximum.
- `/api/v1/pipelines/{id}/observability/capabilities`: explicit provider limitations.

GETs do not invoke external sampling. History explicitly reports gaps/truncation;
charts do not bridge unknown samples or fill missing values with zero. Operational
pipeline/connector/task state remains distinct from telemetry availability. Capture
intent is independent of aggregate DEGRADED state caused by a sink failure. Existing
lifecycle, recovery, authentication and Data Quality remain authoritative.

## Metric capabilities and confidence

Schema version 1 measurements carry nullable value, unit, status, confidence,
observed/collected timestamps, source and reason code. AVAILABLE requires a finite,
valid, attributable value. UNAVAILABLE, UNSUPPORTED, INCONCLUSIVE, PARTIAL and STALE
never carry fabricated numeric results. Explicit exporter timestamps, including
epoch zero, are checked. Measured zero requires fresh complete evidence. A successful
lightweight collection can still contain unavailable provider measurements.

| Measurement | Verified support | Semantics and limits |
| --- | --- | --- |
| Capture delay | PostgreSQL/MySQL, Debezium 3.3.2.Final | `MilliSecondsBehindSource`; source-event versus processing time including clock differences; not destination latency; negative before first event is inconclusive |
| Captured events | Same providers | `TotalNumberOfEventsSeen`; connector counter, never proof of table-specific activity |
| Source connected/event age | Same providers | `Connected`, `MilliSecondsSinceLastEvent`; unique prefix/provider/context and live task/worker attribution |
| Delivery backlog | Kafka Admin, verified Connect groups | Earliest ≤ committed ≤ end for every required partition; offset distance is not necessarily business-row count |
| Sink active/read/send/commit | Connect 4.1.0, trusted JMX | Full live task/worker coverage; counts/rates summed, lag maxima maximized; processing/flush evidence only |
| Sink maximum lag | Conditional JMX | Reference JDBC tasks did not emit `sink-record-lag-max`; unavailable |
| JDBC destination applied/visible | Unsupported | Consumer commits and healthy tasks do not prove durable destination writes |
| Warehouse applied progress | Existing delivery-scoped ledger | Persisted APPLIED/CHECKPOINTED batch only; existing checkpoint semantics; real cloud unverified |
| Snapshot state/rows/chunk | PipelineTable, operations, Debezium notifications | Initial/incremental/resnapshot identity; dedup/order guards; confirmed final rows retained; negative estimates rejected; no estimated-cardinality percentage |
| Snapshot stall | Fresh running/unpaused progress counters | Configured window and at least three samples; notification silence alone is insufficient |
| Other source capture providers | Unsupported telemetry | Existing experimental restrictions unchanged; Oracle/cloud live environments NOT_RUN |
| Collector health | Persisted metadata, `/metrics` | Low-cardinality success/failure gauges for currently tracked pipelines, latest-duration maximum, last success and stale count |

Source series must match a unique provider/prefix/context and a verified live task
on a trusted worker. Sink totals require every live task/worker. Group-name
conventions are candidates only: actual member client IDs, task IDs, assignments
and membership are verified before and after offset reads. Generation changes
invalidate stall continuity. `DescribeTopics` avoids accidental creation of unknown
topics. Telemetry never joins groups, commits/resets offsets or mutates connectors.
Sampling is bounded to 100 topics and 2,048 partitions per delivery.

### Diagnostics and alerts

Findings are deterministic and advisory, with scope, supporting evidence, timestamp,
confidence, explanation and operator action. Sink stalls require complete positive
backlog, unchanged verified offsets, stable generation and at least three consecutive
fresh samples spanning five minutes. Gaps, pause, maintenance, rebalance and reset
invalidate continuity. Capture delay suspicion requires a progressing connector
event counter and makes no table-specific stall claim. Snapshot stalls require fresh
running/unpaused counters throughout the window. Quiet sources and missing telemetry
do not automatically mean stalled or idle.

Five CDC events reuse AlertManager/rules/incidents/channels. Rules must explicitly
select an event. `config_json.observability` validates default capture lag 300000 ms,
backlog 10000, sink window ≥300 seconds and snapshot window ≥900 seconds. Three valid
consecutive samples confirm firing; two confirm recovery. Unknown samples interrupt
counts and never resolve an active threshold incident. Continuity follows configured
cadence, including 300-second intervals. New fingerprints include stable pipeline,
delivery/connector and rule identities; legacy fingerprints remain unchanged.
Recovery details contain recovery evidence. Existing channel/cooldown policy (900
seconds by default) is reused. No notifications activate without explicit rules and
eligible enabled channels.

## Security, UI and backward compatibility

Exporter URLs are deployment-owned cluster/actual-worker settings, never public
request parameters. HTTP clients verify TLS, disable redirects/proxy inheritance,
limit bodies to 2 MiB and support an optional secret bearer token. URLs cannot
contain credentials/query/fragments or arbitrary paths. APIs omit endpoints,
credentials and raw Connect traces. Webhook SSRF restrictions remain enabled.
Real Viewer/Ops/Admin sessions read sanitized results; anonymous requests return
401 and non-Admin alert-rule writes return 403.

Observation does not process CDC payloads, write destinations, trigger snapshots,
change connector configuration, reset offsets, delete slots or change warehouse
checkpoints. Separate acceptance actions intentionally exercise source CRUD,
restarts and owned probe consumers. Retained-prefix deletion touches only a new
probe topic; test consumers commit consumed records and recover natively. Telemetry
never resets a group.

Monitoring adds cached overview/filtering/pagination and pipeline links. Pipeline
Detail adds capture, independent consumer/sink/destination evidence, snapshots,
diagnostics and history. Explicit missing states include timestamp, source and
confidence. Real light/dark screenshots and a 390-pixel mobile viewport verify
rendering without horizontal overflow. Existing navigation, themes, authentication
and independent Data Quality remain intact. See [operator configuration](../operations/monitoring.md).

## Known limitations and release readiness

- **G13 BLOCKED:** no eligible public HTTPS notification endpoint/channel was supplied.
  Real delivery and cooldown remain unverified. SSRF protections were not weakened
  to permit localhost/private webhooks.
- JDBC destination visibility needs independent durable evidence. Kafka commits and
  sink flush timing are not row-correctness or exactly-once guarantees. The reference
  JDBC maximum-lag series remains unavailable.
- Actual Oracle and cloud warehouse environments remain **NOT_RUN**. Existing
  experimental guards remain; ledger unit coverage does not verify a cloud deployment.
- Attribution requires reviewed settings for every actual worker and unique supported
  MBeans. Custom tags/uncovered tasks are inconclusive or partial. Above 100 topics
  or 2,048 partitions, delivery evidence is incomplete. History is seven days/500 points.
- Snapshot counters can be connector-scoped. Missing notifications alone cannot
  prove a stalled table/root cause. Long chunks and waits need investigation.
- No sustained/high-cardinality production benchmark or external deployment was run.

**NO-GO for release.** Finish real eligible-channel delivery/cooldown acceptance
against the recorded source identity before release approval. No automatic recovery
or production deployment was introduced. Both owned Compose projects and the local
Next.js test server have been stopped/removed. No volume-removal option was used.
`artifacts/observability/cleanup.json` records the verified empty project inventories.
`artifacts/observability/evidence-index.json` records checksums, executed command
results and final JUnit totals. All acceptance artifacts are preserved.

# v0.3.3 compatibility and production assessment

The machine-readable matrix is generated by `scripts/cdc_reliability.py`. A
supported capability is distinct from a currently verified E2E path. Every row
separates connection, snapshot, streaming/INSERT/UPDATE/DELETE, data correctness,
recovery and replay. Unsupported source/mode combinations remain rejected by the
existing source and destination guards. No warehouse stateful mode is enabled.

## Verification scope

The local matrix includes PostgreSQL -> PostgreSQL, MySQL -> MySQL, each existing
relational source -> MinIO and ClickHouse, MariaDB -> PostgreSQL/MinIO,
SQL Server -> MinIO, and MongoDB -> MinIO. PostgreSQL/MySQL JDBC checks mean
current-state replication; MinIO and all warehouse checks mean append-only event
history. MongoDB partial patches remain patches, not reconstructed documents.

Cross-database PostgreSQL/MySQL pairs, MariaDB -> MySQL, AWS S3 cloud IAM/network
behavior, and other allowed but unexecuted pairs are candidates rather than new
live certifications. Stateful delivery remains rejected for SQL Server, MongoDB,
Oracle and every warehouse destination. Experimental-source warehouse paths stay
blocked by their existing capability contracts.

The six PostgreSQL/MySQL paths include ordered replay, lifecycle, Connect/Kafka/
control-plane and repeated source outages; ClickHouse/MinIO also include separate
destination outages. JDBC source and destination share a fixture server, so

lifecycle and two short source outages, not the entire primary chaos matrix.
MariaDB and MongoDB outages use explicit existing task restarts. Their correctness
scope is the existing deterministic decimal/Unicode and BSON/patch fixture,
respectively, rather than every type in the primary relational fixture.

The generated JSON contains each allowed candidate and rejected mode as well as
these ten executed pairs. PostgreSQL/MySQL -> BigQuery/Redshift/Synapse are all
NOT RUN, and Oracle live testing is NOT RUN. Local unit guard tests preserve the
rejection of unsupported stateful/source combinations; they are not successful

## Evidence and regression

The baseline before changes was 539 API tests passing with four optional
PostgreSQL skips, plus 93 frontend tests. Current validation also runs those
optional worker lease and legacy migration tests on a separately owned real
PostgreSQL container. UI tests use a freshly built web image and session auth,
including real wizard deployment, readiness, destination rows, pause/resume,
restart, Error Center, audit, invited Ops/Viewer permissions and credential
redaction.

Final executed counts and artifact paths are recorded in the
[E2E report](v0.3.3-e2e-report.md). Development-run failures remain separate from
the final verification: stale fixture auth mode/URLs, mutable Docker port
allocation, early database readiness, mismatched temporal fixture expectations,
and the native SQL dependency defect were reproduced and corrected. No baseline
unit regression was hidden by removing or weakening assertions.

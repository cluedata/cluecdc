## Architecture and compatibility audit

The six source providers live in `app/providers/registry.py`. Connector builders
reuse `services/debezium.py` and the extended provider implementations. Durable
source positions belong to Debezium/Connect. Pipeline lifecycle, operation leases,
topic preparation and source readiness remain in existing services. Effective
keys and type compatibility flow from discovery through sync-strategy assessment
and delivery metadata; tests must not substitute an independent key resolver.

PostgreSQL/MySQL support relational current state and raw object history plus
append-only warehouse history. MariaDB permits PostgreSQL/MySQL upserts and raw
object history. SQL Server, MongoDB and Oracle permit raw object history only.
Warehouse stateful modes and experimental-source warehouse pairs are rejected.
MongoDB patches remain extended JSON, never full-document JDBC upserts.

Snapshot signals and incremental/resnapshot operations use existing source
services. Snapshot progress is derived from Debezium notifications/events, not
connector RUNNING. SQL Server/MongoDB/Oracle online collection operations remain
guarded. Initial snapshot restart behavior differs by source.

Connect owns sink consumer offsets. Managed Redshift/Synapse share
`services/warehouses/staged.py`, the metadata batch ledger and transactional
destination markers. The intended sequence is CREATED -> STAGING -> STAGED ->
APPLYING -> APPLIED -> CHECKPOINTED. Existing tests cover staging failure and
crash after apply/before checkpoint. Recovery of persisted earlier batch states
under changed Kafka poll boundaries needs additional tests. No second checkpoint
authority should be introduced.

Sink recovery uses leased, bounded task restarts, classification/backoff and
desired-state checks. Source-position expiration requires operator recovery;
normal worker retry must not reset offsets. Monitoring uses nullable unsupported
metrics. Existing tests cover RBAC, encrypted secrets, safe previews, audit,
effective keys, source guards, table operations, retention and reconciliation.

## Existing E2E and CI

`source_e2e.py` provisions unique source tables/topics and MinIO buckets, uses
real adapters/builders/Connect, and checks snapshot/CRUD, precision, BSON,
pause/resume and restart. Its optional source outage explicitly restarts tasks;
this is operator-assisted recovery. It does not exercise API orchestration, write
failure reports consistently, or verify all snapshot completion/coordinate claims.
It retains tables/topics/slots/objects and only deletes owned connectors.

`demo.py`, `demo-destination.py` and `demo-object-storage.py` exercise real API
capture/JDBC/MinIO paths but reuse named demonstration resources. Existing CDC
acceptance scripts cover integrity, keys, retention, deletion and recovery.
Frontend Vitest and Playwright cover wizard/lifecycle/auth/destinations.
ClickHouse historical evidence uses synthetic envelopes, not real source CDC.

CI already has fast API/web/security/deployment gates, conditional live CDC/S3/
browser gates, and a dispatch-only extra-source workflow. Preserve these gates;
add reliability scheduling separately with owned projects and sanitized artifacts.
Kubernetes and Compose remain existing deployment targets.

## Prioritized implementation

1. Add persisted staged-batch fault tests; fix reproducible checkpoint/replay defects.
2. Extend acceptance utilities with owned isolation, structured evidence, exact
   snapshot/CRUD checks, and a registry-derived machine-readable matrix.
3. Execute API-driven PostgreSQL/MySQL current state, MinIO and ClickHouse paths
   on isolated real services. Exercise lifecycle and bounded disposable outages.
4. Execute additional sources where available; retain explicit evidence gaps for
   data types, keys, snapshot interruption and source-history expiration.
5. Provide operator-configured cloud runners, dedicated CI and final regression/
   recovery/compatibility reports. Cloud credentials and approved Oracle resources
   are not supplied; do not provision billable resources or infer live success.

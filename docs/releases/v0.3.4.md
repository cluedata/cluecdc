# ClueCDC v0.3.4

Prepared release date: 2026-11-03. Publication is pending candidate validation
and maintainer approval. See the [readiness report](../development/v0.3.4-release-readiness.md)
for the current gate results and remaining release steps.

ClueCDC v0.3.4 adds observational Data Quality checks for relational current-state
tables, plus CDC recovery fixes and isolated reliability acceptance tooling.

## Data Quality

- Open **Operations → Data Quality** to create checks using existing Connections.
  A pipeline is optional. The five-step editor covers datasets, rules, schedules,
  alerts and configuration review.
- Six rules: `row_count`, `row_count_diff`, `last_updated`, `freshness_delay`,
  `data_age` and `schema_match`. Measurements use read-only queries with bounded
  execution, quoted discovered identifiers and bound filter values.
- Verified directions: PostgreSQL → PostgreSQL, MySQL → MySQL and
  PostgreSQL → MySQL. MySQL → PostgreSQL and other provider pairs are blocked.
- Run Now and scheduled execution use durable Jobs and worker leases. Results
  distinguish quality PASS/FAIL/INCONCLUSIVE from execution errors, with history,
  configuration versions, audit events and existing-channel alert delivery.
- Admin manages all actions; Ops can view, configure and run checks; Viewer can
  read checks and history. Delete remains restricted to Admin.

Observations are **BEST_EFFORT**, without a synchronized cross-database snapshot.
Equal counts or timestamps do not prove record equality. Timestamp comparisons
require common declared semantics and explicit timezones for naive values;
MySQL TIMESTAMP measurements use UTC. Source inactivity, ambiguous DST, future
timestamps and unverified capabilities have explicit inconclusive outcomes.

Cross-provider Schema Match certifies integer domain compatibility conservatively.
Known narrowing and timezone-contract changes fail; unverified text, decimal,
date, JSON and other mappings remain inconclusive. A successful value comparison
does not certify schema equivalence. Checks never repair datasets or reset CDC
positions. See [Data Quality](../features/data-quality.md) and the
[cross-provider verification](../development/v0.3.4-data-quality-cross-provider.md).

## Additional CDC sources

This release also includes the source-extension changes merged after v0.3.2:
MariaDB, SQL Server, MongoDB and Oracle appear as **experimental, source-only**
providers using the existing Connections, discovery, readiness, secret storage
and pipeline lifecycle. Connection success alone does not establish CDC readiness.

MariaDB allows guarded PostgreSQL/MySQL current-state delivery and raw S3/MinIO
history. SQL Server, MongoDB and Oracle allow raw object history only; relational
upserts and new-source warehouse pairs remain blocked. MongoDB preserves BSON
identity and patch envelopes without reconstructing relational state. Oracle
uses LogMiner and remains live-unverified; required driver distribution and
database privileges need explicit operator review. New-source snapshot, schema,
recovery and collection-change capabilities retain their documented restrictions.

Local MariaDB, SQL Server and MongoDB evidence covers limited fixture scenarios,
not production certification. Refer to the [source guide](../sources/README.md)
and [current compatibility report](../development/v0.3.3-compatibility-matrix.md)
before enabling any experimental provider. This does not expand Data Quality
beyond its three explicitly verified PostgreSQL/MySQL directions.

## CDC reliability

- Recover staged warehouse batches using their persisted Kafka ranges. Preserve
  applied state if a destination marker is unavailable, and block incomplete or
  expired recovery without advancing checkpoints.
- Report PostgreSQL lost-slot recovery requirements even when Debezium reports
  RUNNING or is not yet assigned. Preserve saved positions for operator recovery.
- Include and build-check native SQL Server/Synapse driver dependencies in the
  API/worker image.
- Add isolated CRUD, replay, outage, interrupted snapshot, expired-WAL and browser
  acceptance runners with structured evidence and a dedicated reliability CI tier.
  These incorporate the unreleased v0.3.3 reliability work; no v0.3.3 publication
  is implied.
- Require the reusable real-database Data Quality, migration and browser workflow
  in release-candidate validation and before tagged image/release publication.

Warehouse destinations retain their documented Preview, append-only history
boundary. Data Quality support does not expand source/destination delivery modes.
Real-cloud warehouse and approved Oracle infrastructure checks require supplied
resources and remain unverified where unavailable. See the
[warehouse capability matrix](../connectors/warehouse-destinations.md).

## Upgrade

1. Back up the metadata database and preserve `SECRET_ENCRYPTION_KEY`. Test
   restoration before changing the deployed version.
2. Stop old API/worker processes before applying metadata migrations. From
   v0.3.2, apply Alembic through **0015**, including the source-provider constraint
   expansion in 0014 and four Data Quality metadata tables in 0015. Use the
   [migration procedure](../development/migrations.md).
3. After publication and deployment approval, deploy matching `0.3.4` API/worker,
   web and Connect images. Kubernetes manifests pin all components to this version;
   workers share the API image. Do not apply these image references before the
   release images exist.
4. Confirm API/worker health, migration revision, existing pipeline/delivery state,
   roles and alert channels. Create a manual check with approved read-only database
   access, review capability validation, then inspect its completed history.
5. Enable schedules and notifications only after reviewing query cost, timestamp
   semantics, thresholds and Source activity expectations for each dataset.

Migration 0015 adds control-plane metadata only; it does not alter Source or
Destination tables or rewrite existing CDC metadata. Downgrading 0015 removes
Data Quality configuration/history; export required evidence first. Revision 0014
refuses downgrade while additional source-provider Connections still exist.
Do not treat a database downgrade as a lossless application rollback.

## Validation and publication boundary

Local verification includes all six rules against disposable PostgreSQL/MySQL
databases, API/worker behavior, RBAC, UI navigation and real browser sessions.
Recorded pre-preparation evidence contains **739 backend tests**, **96 frontend
tests**, three Data Quality browser cases and isolated migration round trips.
The [readiness report](../development/v0.3.4-release-readiness.md) records the new
release gate separately from this earlier evidence.

Local results do not identify an immutable release candidate. A clean reviewed
commit, successful release-candidate CI, target-environment review and authenticated
GitHub/GHCR availability checks are required before an approved signed release tag.
No images, tags or GitHub Release are published by this preparation.

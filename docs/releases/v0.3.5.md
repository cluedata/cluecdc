# ClueCDC v0.3.5

Release metadata prepared on 2026-11-11. Publication remains blocked on real
HTTPS notification-channel acceptance, candidate validation and maintainer
approval. Prepared metadata does not establish that release artifacts are published.
See the [release-readiness report](../development/v0.3.5-release-readiness.md).

ClueCDC v0.3.5 adds measured CDC observability and advisory pipeline diagnostics
for PostgreSQL/MySQL deployments using trusted Debezium/Kafka Connect exporters.
Operational progress, consumer commits and destination correctness remain distinct.

## CDC Observability

- **Source capture:** Debezium processing delay, captured-event counters,
  source connectivity and event age, with task/worker identity and timestamps.
  Capture delay is not end-to-end destination replication latency.
- **Kafka backlog:** targeted read-only offset sampling for verified delivery
  groups, with partition coverage and explicit rebalance/retention/missing-offset
  states. Partial coverage never becomes a complete total.
- **Sink progress:** independent processing/flush counters for each delivery,
  requiring full task/worker coverage. Kafka commits do not prove destination writes.
- **Snapshot visibility:** existing initial/incremental/resnapshot metadata and
  notifications, protected against duplicate and out-of-order progress events.
- **Diagnostics:** evidence-based capture-delay, backlog and snapshot/sink-stall
  findings. Missing telemetry and quiet sources do not automatically mean stalled.
  Suggestions are advisory; observability performs no automatic recovery.
- **History:** seven-day raw retention by default, bounded UTC queries with at
  most 500 points, explicit gaps and no invented zero values or interpolation.

## Alerts, API and UI

Five explicit CDC event types reuse existing alert rules, incidents and notification
channels. Firing requires three valid consecutive samples; recovery requires two.
Telemetry loss does not resolve active threshold incidents. Notifications require
explicit rules and eligible enabled channels; real channel cooldown acceptance
is still a release blocker.

Monitoring adds cached overview/filtering. Pipeline Detail adds an Observability
tab with capture, delivery, snapshot, diagnostics and history evidence in light/dark
themes and responsive layouts. Four authenticated read endpoints expose summary,
pipeline observation, history and provider capabilities using `pipelines.read`.
GET requests do not trigger live provider sampling.

## Security and compatibility

Additive migration **0016** preserves existing metadata and legacy metric rows.
The collector uses durable PostgreSQL leases/fencing, idempotent sample buckets,
bounded timeouts/backoff and a shared four-collection concurrency ceiling.
Exporter settings are deployment-owned, never arbitrary public request URLs.
Secrets, exporter endpoints and raw Connect traces are excluded from public results.
Existing RBAC, webhook SSRF protections, lifecycle and Data Quality remain in place.

Observation never changes source data, destinations, connector configuration,
Kafka offsets, replication slots or warehouse checkpoints.

## Fixes

- Use mapped destination column types for PostgreSQL-to-MySQL preparation while
  retaining compatibility with legacy native-type metadata.
- Preserve CDC alert thresholds when older clients omit `config_json` on updates.
- Evaluate capture intent independently of sink-related DEGRADED pipeline state.
- Use database time consistently for collector scheduling and lease fencing.
- Recognize observability infrastructure in scoped CI and build its Connect base
  before the derived exporter image.

## Known limitations

- JDBC applied/visible progress remains unsupported without independent durable
  destination evidence. The reference JDBC tasks do not expose every sink metric.
- A local JSONB demo required a PostgreSQL JDBC URL parameter adjustment. This is
  a demo workaround, not a shipped fix; deployment-specific JSONB delivery needs
  review before final release approval.
- Experimental source/provider restrictions remain unchanged. Oracle and actual
  cloud warehouse environments remain live-unverified where infrastructure was
  not supplied. Persisted ledger evidence does not certify a cloud deployment.
- Capture/sink metrics require reviewed exporter mappings for every actual worker.
  Delivery sampling is bounded to 100 topics and 2,048 partitions.

## Upgrade preparation

1. Back up metadata and verify restoration; preserve `SECRET_ENCRYPTION_KEY` and
   existing credentials, Kafka state, slots and warehouse checkpoints.
2. Test the upgrade in an isolated environment. Stop old API/worker processes
   before applying Alembic **0015 → 0016** using the documented
   [migration procedure](../development/migrations.md).
3. After publication and approval, update API/worker, web and Connect to the exact
   published `0.3.5` images. Workers continue using the API image. No `0.3.5`
   image availability is asserted by these notes.
4. Configure the optional trusted JMX integration through
   [monitoring configuration](../operations/monitoring.md). A Prometheus Server
   is not required. Validate task coverage and freshness after rollout.

Downgrade removes the new collection cache and snapshot provenance fields; legacy
metadata and metric values are retained. Review rollback in a disposable copy
before changing a deployed installation. Never reset offsets or delete volumes
as an upgrade shortcut.

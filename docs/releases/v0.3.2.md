# ClueCDC v0.3.2 — Warehouse destinations

ClueCDC v0.3.2 adds Preview append-only CDC history destinations for Google
BigQuery, Amazon Redshift, ClickHouse, and Azure Synapse Dedicated SQL Pool.
Existing PostgreSQL, MySQL, S3, and MinIO behavior remains unchanged.

## Highlights

- Destination-only Connection CRUD, encrypted provider credentials, Test
  Connection diagnostics, capability-aware forms, and delivery creation for all
  four warehouses.
- Checksum-pinned ClickHouse 1.7.0 and Apache-2.0 Aiven BigQuery 2.15.0 Kafka
  Connect sinks plus a fixed-schema Debezium history transformation.
- Managed S3/Redshift and Azure Storage/Synapse staged COPY runtimes integrated
  with the existing delivery lifecycle.
- A shared durable batch state machine, destination-side application markers,
  replay deduplication, and Kafka checkpoint gating.
- Fixed-history-schema validation that rejects incompatible existing tables
  without dropping columns, changing types, or rebuilding production tables.
- An optional ClickHouse 26.8 LTS Compose profile for local integration tests.

## Warehouse capability boundary

All four destinations support append-only event history only. History rows keep
Kafka topic, partition, offset and timestamp together with the Debezium
operation, key, before, after, and source documents.

Current-state upsert/delete application is not supported. ClueCDC rejects that
mode instead of silently converting it to append-only. Automatic source-schema
evolution is also disabled; target tables use the documented fixed schema.

ClickHouse runs at-least-once by default. The connector's Keeper-backed
exactly-once mode is not enabled automatically, so replayed rows can be
identified by topic, partition, and offset. Redshift and Synapse checkpoint
Kafka only after the target transaction writes a destination batch marker.

See the [warehouse capability matrix](../connectors/warehouse-destinations.md)
for evidence and per-destination limitations.

## Upgrade

1. Back up the metadata database and `SECRET_ENCRYPTION_KEY`.
2. Apply Alembic migrations through revision `0013`. Existing Synapse ledger
   rows are translated and the table is renamed to `warehouse_batch_ledger`.
3. Deploy the `0.3.2` API/worker and web images.
4. Rebuild or deploy the `0.3.2` Connect image on every worker so the pinned
   ClickHouse/BigQuery plugins and ClueCDC history SMT are available.
5. Confirm `/connector-plugins`, then test every warehouse connection and a
   non-production delivery before enabling operational workloads.

## Deployment notes

- Kubernetes continues to treat PostgreSQL, Kafka, Kafka Connect, and cloud
  warehouses as external services.
- Redshift and Synapse workers require private egress to Kafka, object storage,
  and the warehouse SQL endpoint.
- Use S3/Azure lifecycle policies scoped to the delivery staging prefix; v0.3.2
  does not include an automatic staging cleanup worker.
- Do not enable or resume paid cloud resources automatically for validation.

## Validation status before publication

The local quality suite, image build/plugin discovery, and real local
ClickHouse sink/restart/outage checks pass. Real BigQuery, Redshift, and Azure
Synapse cloud E2E and the complete PostgreSQL/MySQL-to-warehouse source matrix
remain NOT RUN without operator-supplied resources. Treat the four warehouse
destinations as Preview and complete those environment-specific checks before
approving a production rollout.

# ClueCDC v0.2.1

Unreleased draft. ClueCDC `v0.2.1` hardens the `v0.2.0` control plane while
retaining existing sources, destinations, and Viewer/Ops/Admin roles. CDC
records stay in the Debezium/Kafka/Connect data plane, never the ClueCDC API.
Review the configuration and deployment changes before upgrading this `0.x`
release; local acceptance is not general production approval.

## Highlights

- Stricter production configuration, browser sessions, and Kafka security.
- Live CDC integrity, snapshot, retention, and failure-recovery verification.
- Bounded worker retries and serialized connector lifecycle operations.
- Verified metadata backup/restore, guarded upgrades, and a hardened Kubernetes
  application baseline with mandatory release acceptance gates.

## Security

- Production startup validates HTTPS origins, authenticated PostgreSQL, unique
  strong service secrets, session authentication and disabled demo bootstrap.
- Browser sessions use secure cookie attributes, explicit origin checks for
  state-changing requests and hardened response headers. Logout requires
  authentication and revokes only the current session.
- Login throttling is shared across API replicas. Role/account changes invalidate
  existing sessions; route/RBAC regression tests enforce the server boundary.
- Kafka clients support verified TLS/mTLS and SASL PLAIN, SCRAM-SHA-256, and
  SCRAM-SHA-512. ClueCDC-managed credentials and TLS material are encrypted in
  metadata; connector settings use ConfigProvider references. Connect worker
  credentials remain independent deployment configuration. Production rejects
  unencrypted Kafka transport by default.
- Broader redaction covers APIs, previews, audits, jobs, alerts, and runtime
  errors; encrypted credential rotation is verified. See [Kafka configuration](../connections/kafka.md)
  for worker inline PEM setup and inherited file-store limitations.

## CDC integrity and recovery

- Live acceptance reconciles all four PostgreSQL/MySQL source-to-JDBC paths:
  snapshots, streaming CRUD, transactions, primary-key updates, Unicode, NULL,
  decimals, and timestamps. MinIO checks verify keyed create/update/delete JSONL
  envelopes; these tests do not establish AWS S3 environment compatibility.
- Restart/outage tests cover connector tasks, Connect, API, workers, Kafka,
  and PostgreSQL: offsets and connector configuration are retained without
  implicit reset or resnapshot. Missing history produces recovery hints.
- Snapshot coverage includes table add/remove isolation, explicit resnapshot,
  interruption, and cancellation. Schema history classifies breaking changes;
  compatible destination columns are added, and unsupported mappings rejected.
- Non-mutating diagnostics report PostgreSQL slot/WAL and MySQL binlog retention
  risk, permission-limited visibility, and retention-alert recovery.

## Reliability

- Reconciliation isolates resource failures and preserves pause/stop intent
  during dependency outages without hiding failures.
- Workers persist error classification, bounded exponential retries with jitter,
  attempt history, and manual terminal-job retry. Known permanent errors do not
  enter automatic retry loops.
- Job and connector-operation leases suppress competing work. Deterministic
  deploy retries adopt only an exact existing connector configuration; external
  effects and metadata commits are not globally atomic.

## Kubernetes and production deployment

The production Kustomize base deploys web/API/worker only. Supply external
PostgreSQL/Kafka/Connect, private secret callbacks, TLS ingress, and Secrets.
Bundled metadata/Connect manifests remain development references, excluded
from the base.

The application pods use non-root restricted security contexts, read-only root
filesystems, bounded scratch volumes, resource requests/limits, startup and
health probes, and graceful shutdown. Each tier defaults to two replicas, not
a dependency HA guarantee. Default-deny ingress permits public web access and
approved private API clients; egress policy is operator-owned.

See the [Kubernetes deployment guide](../deployment/kubernetes.md) for external
endpoints, Secrets, callback networking, overlays, and rollout validation.

## Upgrade notes from v0.2.0

During a maintenance window, stop the old API/workers while keeping the data
plane intact. Use the v0.2.1 checkout with Python dependencies and compatible
PostgreSQL clients. Supply `DATABASE_URL` and the original
`SECRET_ENCRYPTION_KEY` through the environment, not command arguments.

```bash
python scripts/metadata_backup.py backup --output /secure/cluecdc-pre-v021.dump
python scripts/metadata_backup.py verify --dump /secure/cluecdc-pre-v021.dump
python scripts/metadata_upgrade.py preflight
python scripts/metadata_upgrade.py upgrade --backup-dump /secure/cluecdc-pre-v021.dump
```

The guarded `0003` → `0004` → `0005` → `0006` upgrade checks schema drift,
decryption, counts, identities, and ciphertext; rerunning at head is idempotent.
Released migrations are unchanged. Do not stamp revisions or bypass failures.

Before restarting services:

1. Set `ENVIRONMENT=production`, `AUTH_MODE=session`, disable demo bootstrap,
   and review HTTPS `PUBLIC_URL`/`CORS_ORIGINS` and production-compliant Secrets.
2. Configure external PostgreSQL/Kafka/Connect, private callbacks, network
   selectors, and pinned images. Configure Connect worker/internal clients
   separately from registered Kafka credentials and Connect REST authentication.
3. Retain existing named accounts; use the interactive Admin CLI only when
   needed. Check readiness, login/roles, secret resolution, and representative
   source/destination catch-up before ending the maintenance window.

See [metadata migrations](../development/migrations.md) for the full procedure.

## Backup and restore

Backups use PostgreSQL custom archives with checksum/revision manifests; keep
the key separately. Set `RESTORE_DATABASE_URL` to a new empty `cluecdc_restore`
database and retain the original encryption key:

```bash
python scripts/metadata_backup.py restore \
  --dump /secure/cluecdc-pre-v021.dump \
  --target-database-url-env RESTORE_DATABASE_URL \
  --confirm-target-database cluecdc_restore
```

Wrong keys and nonempty targets are rejected; restored metadata is migrated
and verified. On upgrade failure, validate an isolated restore before cutover;
safe production downgrade is not claimed. Backups exclude Kafka offsets/internal
state, source history, and destination data. Follow the
[backup/restore runbook](../operations/backup-restore.md) before resuming.

## Compatibility and breaking changes

- No intentional source/destination API or Viewer/Ops/Admin permission changes.
- Production validation is stricter and can reject configurations previously
  accepted, including development credentials or insecure Kafka transport.
- The Kubernetes base no longer deploys bundled metadata PostgreSQL or Connect.
  Existing installations must supply external dependencies and review overlays.

## Docker images

After maintainer approval, the tag-triggered workflow is configured to publish:

- `ghcr.io/cluedata/cluecdc-web:0.2.1`, `:0.2`, and `:latest`
- `ghcr.io/cluedata/cluecdc-api:0.2.1`, `:0.2`, and `:latest`
- `ghcr.io/cluedata/cluecdc-connect:0.2.1`, `:0.2`, and `:latest`

These are planned references, not confirmation of publication. Workers use the
API image; external Connect needs the ClueCDC plugins/ConfigProvider.
Pin `0.2.1` or a verified digest; `:0.2` and `:latest` are moving aliases.
Immutable release versions must not be rebuilt.

## Known limitations

- Delivery remains at least once. Keyed JDBC upserts make materialized replay
  idempotent; object-storage consumers must handle duplicate events.
- Unsupported types and breaking schema changes require operator decisions.
  Lost retained history is not repaired by automatic offset reset/resnapshot.
- SSO/OIDC and invitation email delivery are not implemented. Broker ACLs,
  Connect REST authentication, key lifecycle, external-secret synchronization,
  backups, and dependency availability remain operator responsibilities.
- Recorded production npm and Python dependency scans passed. The full npm tree
  retains five high-severity development-only findings in the
  [documented braces/ESLint dependency chain](../development/control-plane-refactor-audit.md#dependency-audit-limitation).
  The full-tree critical gate passed; review this exception before promotion.

## Validation and release status

Recorded local validation: 250 API tests, 48 web unit tests, 9 browser tests,
14 combined live stages, 22 Kafka security checks, and all four authenticated
JDBC paths passed. Isolated kind/Calico/NGINX tests verified rollout, HTTPS
sessions, and NetworkPolicy allow/deny/revocation. The
[hardening report](../development/v0.2.1-hardening-progress.md) records evidence
and candidate SHAs; these results are not remote CI or target-cluster approval.

The release workflow requires live/Kubernetes gates before publication. Pilot
promotion still requires remote CI on the exact release commit and operator
review of target networking, TLS, identities, capacity, and recovery.
Preparation creates no tag or release.

# ClueCDC v0.2.1 — release-notes draft

Unpublished hardening candidate based on v0.2.0. This draft records implemented
behavior; it is not a claim that an arbitrary production environment is ready.
The [hardening progress report](../development/v0.2.1-hardening-progress.md)
records executed checks and remaining acceptance evidence.

## Security

- Production startup validates HTTPS origins, authenticated PostgreSQL, unique
  strong service secrets, session authentication and disabled demo bootstrap.
- Browser sessions use secure cookie attributes, explicit origin checks for
  state-changing requests and hardened response headers. Logout requires
  authentication and revokes only the current session.
- Login throttling is shared across API replicas. Role/account changes invalidate
  existing sessions; route/RBAC regression tests enforce the server boundary.
- Kafka administration, source producers, MySQL schema-history clients, sink
  consumers and independently configured Connect workers support TLS and SASL.
  PLAIN and SCRAM credentials, private CAs and optional client certificates stay
  encrypted in metadata and are resolved through the existing ConfigProvider.
- Secret redaction and credential rotation cover APIs, previews, audits, jobs,
  alerts and runtime errors. Worker TLS uses the documented inline PEM provider
  setup to avoid inherited file-store conflicts with connector credentials.

## Correctness and recovery

Live acceptance covers PostgreSQL/MySQL sources against both JDBC destinations,
plus MinIO JSONL event envelopes. It exercises snapshots, streaming CRUD,
transactions, primary-key changes, Unicode, NULL, decimals and timestamps.

Snapshot/table operations reject unsupported or breaking schema changes,
preserve pause intent across outages and require explicit resnapshot/recovery.
Retention diagnostics report PostgreSQL slot/WAL and MySQL binlog risk without
changing source logging configuration or deleting slots.

Workers persist classified failures, bounded exponential retries with jitter,
attempt history and manual terminal retry. Job and connector-operation leases
serialize competing work; deterministic deployment retries adopt only an exact
existing connector configuration. Dependency failures remain visible.

## Deployment and upgrades

The production Kustomize base now deploys application tiers only. Operators must
provide external PostgreSQL, Kafka and Kafka Connect, private secret callbacks,
TLS ingress and externally supplied Secrets. Existing bundled metadata/Connect
files remain development references and are no longer base resources.

Containers run non-root with restricted security contexts and read-only root
filesystems, bounded temporary volumes, resource bounds, startup/health probes
and shutdown grace periods. The application tiers default to two replicas.
An isolated kind/Calico/NGINX acceptance job checks rollout, network policy
allow/deny/revocation and production HTTPS session boundaries before release
publication jobs can proceed.

Before upgrading from v0.2.0:

1. Stop metadata-changing control-plane actions for the maintenance window.
2. Create and verify a PostgreSQL backup and preserve the exact encryption key
   separately. Follow [backup and restore](../operations/backup-restore.md).
3. Run the guarded [upgrade preflight](../development/migrations.md). Revision
   `0003` upgrades through `0004`, `0005`, and `0006`; counts, identities,
   ciphertext, secret decryption and schema drift are checked.
4. Review the production [Kustomize changes](../deployment/kubernetes.md),
   external endpoints, NetworkPolicy selectors and immutable image references.
5. Configure Connect worker/internal/producer/consumer TLS/SASL independently
   from ClueCDC's registered cluster credentials and Connect REST authentication.
6. Create the first production Admin with the interactive CLI where required,
   check readiness, and run representative source/destination recovery tests.

On upgrade failure, restore the verified backup into a new empty database and
perform a controlled cutover. A safe production downgrade is not claimed.

## Compatibility and remaining limits

- Existing source/destination APIs and Viewer/Ops/Admin permissions are retained.
  Production configuration and private deployment requirements are stricter;
  the Kustomize topology change requires operator review during upgrades.
- Delivery remains at least once. Keyed JDBC upserts make materialized replay
  idempotent; object-storage consumers must handle duplicate events.
- Unsupported types and breaking schema changes require operator decisions.
  Lost retained history is not repaired by automatic offset reset/resnapshot.
- Encryption-key rotation, SSO/OIDC, broker ACL provisioning, Connect REST
  authentication and external-secret synchronization remain operator concerns.
- Offline Kubernetes schema/policy checks and Docker runtime tests do not prove
  a target cluster's CNI, ingress, TLS, availability or network enforcement.
- Local production npm and Python dependency scans pass. The full npm tree
  retains five high-severity development-only findings in the
  [documented braces/ESLint dependency chain](../development/control-plane-refactor-audit.md#dependency-audit-limitation).
  The full-tree critical gate passes; maintainers must review this exception
  before promotion. Functional tests do not establish a clean dependency audit.

The reusable hardening workflow runs isolated live security, CDC, recovery,
metadata and container tests before release publication jobs can proceed.
Maintainers must still approve the exact release commit and environment evidence.
No tag, image or release is created during local preparation.
